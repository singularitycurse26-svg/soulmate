# ACELINE UNIVERSAL AUTO-FIT, CAPACITY, QUANTIZATION, PERFORMANCE PROTECTION & SELF-WRITING ADAPTIVE SYSTEM RULE

## MASTER RULE
Whenever Aceline creates, modifies, clones, ports, repairs, updates, optimizes, or operates ANY software: Aceline MUST automatically determine how much information the environment can safely display, process, store, transmit, remember, and execute, and automatically adapt the software to those limits.

This applies to: UI, CLI, webpage, terminal, telegram, backend, database, memory, journal, LLM context, project files, storage, network, CPU, GPU, RAM, VRAM.

## ULTIMATE LOOP
CREATE -> RUN -> OBSERVE -> MEASURE -> FIT -> QUANTIZE -> OPTIMIZE -> DETECT -> SUGGEST -> PLAN -> SELF-WRITE -> TEST -> VERIFY -> APPLY -> JOURNAL -> REMEMBER -> LEARN -> IMPROVE -> REPEAT FOREVER

## FINAL OBJECTIVE
BUILD SOFTWARE THAT CAN BUILD SOFTWARE, OBSERVE SOFTWARE, UNDERSTAND SOFTWARE, ADAPT SOFTWARE, OPTIMIZE SOFTWARE, TEST SOFTWARE, REPAIR SOFTWARE, AND CONTINUE IMPROVING SOFTWARE WHILE KEEPING THE UI, DATA, MEMORY, STORAGE, COMPUTATION, AND INFORMATION FLOW WITHIN SAFE OPERATING LIMITS.

## 115 Rules (Summary)

### Fundamentals (1-8)
1. Never assume "works on my machine = finished." Ask: does it fit? display correctly? remain responsive? work with more/less data/screen/hardware? recover from pressure? adapt?
2. Four primary surfaces (UI, CLI, webpage, terminal) are one system sharing memory, journal, backend, task engine, observation engine, capacity engine, self-writing engine.
3. Never treat the four surfaces as separate brains. Cross-surface workflows = ONE WORKFLOW.
4. Universal Capacity Engine: continuously understand current load, available capacity, expected load, safe/warning/critical limits for every resource.
5. Capacity is not one number. 100GB storage != 100GB RAM != 100GB UI data != 100GB LLM context.
6. Resource types: screen, window, viewport, DOM, UI components, CLI/terminal output, text, instructions, LLM tokens, memory, RAM, VRAM, CPU, GPU, storage, database, network, cache, logs, files, queues, tasks, concurrency.
7. Universal Resource Model: current, available, soft_limit, warning_limit, hard_limit, critical_limit, trend, projected_load, recommended_action.
8. Three questions before large operations: can this fit? run fast enough? continue working as it grows? If no: ADAPT BEFORE EXECUTION.

### Screen & UI Auto-Fit (9-14)
9. Screen auto-fit: respond to width, height, window size, display scale, font scale, orientation, zoom, device type.
10. Responsive design is automatic: auto-determine desktop/laptop/tablet/phone/small window/large monitor.
11. Auto-reflow: wide -> compressed -> stacked -> collapsed -> scrollable. Interface remains usable.
12. Auto-fit text: account for long/short text, large/small font, zoom, translation, accessibility. No overflow/overlap/breakage.
13. Auto-fit components: min/max width/height, flexibility, collapse rule, overflow rule.
14. Table auto-fit: full table, horizontal scroll, column collapse, column priority, stacked row, pagination, virtualization.

### Data Quantization (15-26)
15. Massive data: don't render every record. Full data -> index -> filter -> sort -> active window -> render.
16. Data quantization: chunking, pagination, windowing, virtualization, streaming, summarization, compression, caching, archiving, deferred loading.
17. Full data vs active data: FULL = everything available, ACTIVE = what's needed, VISIBLE = what's displayed.
18. Virtualization: 1M items -> visible window -> 20-100 active components. Recycle on scroll.
19. Pagination: database retrieves only requested portion.
20. Server-side data control: database -> query -> filter -> sort -> limit -> chunk -> webpage.
21. Terminal quantization: summary + relevant output + full log location. Not endless rendering.
22. CLI quantization: --limit, --page, --offset, --filter, --summary, --verbose, --output, --json, --stream.
23. Terminal scrollback: current -> scrollback -> log file -> compressed archive.
24. Webpage quantization: control DOM size, JS memory, network payload, images, data, event handlers, animations.
25. Lazy loading: don't load expensive content until needed.
26. Progressive loading: critical UI -> primary -> secondary -> optional.

### Storage & Context (27-42)
27. Storage capacity: track total/used/free across database, cache, logs, projects, temp, backups, archives.
28. Storage thresholds: normal (<70%), warning (70-85%), high (85-95%), critical (>95%). Configurable.
29. Storage protection: cache cleanup, log rotation, temp cleanup, compression, archiving, DB maintenance. Never auto-delete project data without authorization.
30. Data lifecycle: active -> warm -> cold -> archived.
31. LLM context quantization: search -> rank -> filter -> summarize -> inject relevant context. Not entire memory + journal + project + codebase.
32. Instruction budget: separate system/project/task rules, user request, relevant memory/journal/files, tool output.
33. Context hierarchy: L0 current request, L1 current task, L2 current project, L3 relevant memory, L4 relevant journal, L5 archived history. Retrieve deeper only when necessary.
34. Active working set: only what's needed (e.g., 8 files, 3 components, 2 tests, 1 schema, 1 config).
35. Automatic working-set expansion: detect missing -> search -> retrieve -> add.
36. Automatic working-set shrinking: remove no-longer-relevant from active context. Remains stored.
37. Context safety reserve: never use 100% of LLM context. Reserve for new instructions, tool output, errors, verification, final response.
38. Context compression: raw history -> important events -> decisions -> current state -> summary. Full history stored.
39. Instruction deduplication: replace redundant repeated instructions with canonical reference.
40. Large codebase quantization: project -> index -> search -> relevant files -> relevant symbols -> active working set.
41. Code index: files, functions, classes, modules, dependencies, imports, exports, routes, components, DB models, tests, config.
42. Incremental processing: one file changes -> identify dependencies -> process affected area. Don't rebuild everything.

### Performance & Capacity (43-61)
43. Performance budget: render time, memory, CPU, network, DOM count, component count, active requests, context size, queue size.
44. Bottleneck detection: RAM, CPU, GPU, storage, network, database, DOM, JS, LLM context, disk I/O. Optimize bottleneck first.
45. Pre-flight capacity check: estimate cost -> compare to capacity -> safe? execute : quantize.
46. Adaptive execution: direct, chunk, page, stream, virtualize, cache, defer, background, summarize, archive.
47. Backpressure: if produced faster than consumed, slow/pause producer.
48. Queue protection: max size, priority, timeout, retry limit, failure handling. No infinite queues.
49. Concurrency control: more parallel != faster.
50. Background processing: indexing, archiving, full tests, large imports/exports, analytics.
51. Progress feedback: started, progress, current step, estimated remaining, completed, failed.
52. Graceful degradation: full -> reduce optional -> paginate -> virtualize -> background -> safe mode. Don't crash.
53. Emergency resource protection: stop noncritical -> save state -> release unused -> reduce load -> notify -> recover.
54. Growth testing: current, 10x, 100x, expected future.
55. Scale risk detection: current size, expected size, bottleneck, failure mode, recommended solution.
56. Automatic side notes: UI overload, data growth, slow rendering, large output, large context, storage/network pressure, duplicated instructions, repeated operations.
57. Automatic suggestions: side note -> pattern -> suggestion -> task.
58. Automatic execution: suggestion -> task -> plan -> implement -> test -> measure -> verify -> journal.
59. Memory: store durable lessons (pagination strategy, virtualization, log locations, etc.).
60. Journal: problem, detection, action, before/after metrics, result, failure, rollback.
61. Telegram: capacity warnings, automatic optimizations, critical events, approval requests, performance improvements.
