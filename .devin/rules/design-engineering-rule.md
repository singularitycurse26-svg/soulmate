# UNIVERSAL DESIGN, LAYOUT, VISUAL SYSTEM & FUNCTIONALITY ENGINEERING RULE

## MASTER PURPOSE
Whenever creating, recreating, redesigning, inventing, improving, replacing, cloning, porting, extending, or reverse-engineering a software product, website, application, interface, dashboard, operating environment, workflow, tool, service, feature, or digital system:

**DO NOT TREAT DESIGN AS DECORATION.**
Design must be treated as an engineered system.

## MASTER RULE
BUILD THE EXPERIENCE, NOT JUST THE INTERFACE.

## THE ULTIMATE STANDARD
FUNCTIONAL + UNDERSTANDABLE + CONSISTENT + RESPONSIVE + ACCESSIBLE + RECOVERABLE + EFFICIENT + VISUALLY COHERENT + PURPOSEFUL + TESTED

## 75 Rules (Summary)

1. Design Is A System, Not A Picture — design the entire state machine
2. Functionality Has Priority Over Cosmetics — FUNCTION -> INFORMATION -> STRUCTURE -> VISUAL DESIGN -> POLISH
3. Perform A Design Forensic Analysis — analyze global structure, positioning, spatial relationships
4. Reconstruct The Layout Hierarchy — Primary Structure -> Functional Sections -> Components -> Micro-elements
5. Create A Spacing System — consistent spacing scale (4px, 8px, 12px, 16px, 24px, 32px, 48px, 64px)
6. Create A Design Grid — columns, gutters, margins, breakpoints
7. Create A Responsive Design Model — reorganize for different spatial constraints
8. Build A Complete Color System — primary, secondary, background, text, border, status
9. Do Not Use Color Only Because It Looks Good — every color must have a purpose
10. Create A Color Token System — centralize color definitions
11. Analyze Color Relationships — background vs text, button vs background, etc.
12. Typography Is Part Of Functionality — font, size, weight, line height, spacing
13. Create A Typographic Hierarchy — Display, H1-H3, Body, Caption, Label, Micro Label
14. Text Must Be Designed For Real Content — test with long names, numbers, dates, missing values
15. Create A Component Language — buttons, inputs, cards, menus should feel related
16. Button Engineering — shape, size, states, hierarchy (Primary, Secondary, Tertiary, Destructive)
17. Interaction States Must Be Designed — default, hover, focus, pressed, disabled, loading, success, error
18. Design The User's Attention — guide eyes with size, contrast, position, whitespace
19. Group Related Information — proximity, containers, headings, separators
20. Design Navigation As A Map — where am I? where can I go?
21. Preserve User Context — don't reset forms, move users, or erase info unnecessarily
22. Design Feedback Into Every Action — never leave users wondering "did it work?"
23. Loading States Are Part Of The Design — spinner, skeleton, progress, retry
24. Error States Must Be Engineered — what happened, why, what to do next
25. Empty States Must Have Purpose — explain what normally appears, why empty, what to do
26. Design Destructive Actions Differently — warning, confirmation, undo, recovery
27. Analyze Iconography — coherent icon language, don't mix families
28. Design Icon + Text Relationships — size, gap, alignment, decorative vs functional
29. Design Cards And Containers — background, border, shadow, radius, padding, states
30. Control Visual Density — find density appropriate to the task
31. Design The Z-Axis — base, content, sticky, floating, modal, notification layers
32. Design Depth Intentionally — shadows, borders, elevation, contrast, blur, overlays
33. Design Motion — purposeful animations: transition, cause/effect, state change, progress
34. Design Transitions Between States — closed->open, loading->complete, collapsed->expanded
35. Never Create A Dead End Without A Reason — where did user come from, where can they go
36. Design The Complete Workflow — trace entire journeys, every transition
37. Design For The User's Goal, Not The Screen — shortest clear path to accomplish goal
38. Minimize Cognitive Load — visible context, sensible defaults, recognizable controls
39. Create Consistency Rules — similar components behave similarly
40. Create Exceptions Only Intentionally — every exception must answer "why is this different?"
41. Design Accessibility Into The Original System — keyboard, contrast, screen-reader, touch targets
42. Design Touch And Pointer Interaction — desktop vs mobile interaction models
43. Design Keyboard Workflows — tab order, shortcuts, Enter/Escape, focus restoration
44. Design Information Architecture — what belongs together, what's hidden, what's searchable
45. Design Search — input, loading, results, no-results, error, clear/reset states
46. Design Data Presentation — choose best format: text, list, table, chart, card, timeline, graph
47. Design For Real-World Failure — network failure, invalid input, missing data, expired sessions
48. Design Recovery — retry, undo, restore, edit, cancel, go back, reconnect, reload
49. Design Persistence — what survives navigation, refresh, restart, logout, device change
50. Design Personalization — theme, layout, notifications, density, language, shortcuts
51. Design Dark And Light Modes As Systems — don't just invert colors
52. Design Visual Identity — color, typography, shape, icon, spacing, motion, imagery identity
53. Do Not Randomly Copy Visual Elements — analyze underlying design principles
54. Differentiate When Creating An Original Invention — explore better interaction models
55. Use Reverse-Engineering Thinking — observed result -> interaction -> component -> state -> logic -> data -> architecture
56. Functionality Must Match Visual Communication — never create a visual lie
57. Design Micro-Interactions — button press, checkbox, dropdown, tab switch, drag and drop
58. Design Perceived Performance — immediate feedback, optimistic updates, skeletons, streaming
59. Design Automation Visibly — user understands what system is doing, waiting for, completed
60. Human Control Must Remain Clear — what's automatic, what needs confirmation, what can be stopped
61. Design Progressive Disclosure — show important controls first, reveal advanced when needed
62. Design For Expert Users — shortcuts, command palettes, bulk actions, templates
63. Test The Design With Task Scenarios — measure steps, confusion, errors, time
64. Conduct A Visual QA Pass — alignment, spacing, typography, color, components, motion
65. Conduct A Functional QA Pass — every button, link, input, menu, form, state
66. Conduct A State QA Pass — initial, empty, loading, success, error, disabled, partial, offline
67. Conduct A Responsive QA Pass — overflow, clipped text, overlapping controls, broken nav
68. Conduct A Blind User Test — "would I know what to do if I saw this for the first time?"
69. Conduct A Power User Test — "is it still efficient after hundreds of uses?"
70. Conduct A Failure User Test — invalid inputs, canceling, disconnecting, unexpected data
71. Create A Design Specification Before Final Implementation — 25-point spec
72. Never Patch Design Randomly — find root cause, not symptom
73. Prefer Systemic Fixes — fix the shared rule, not individual components
74. Design Tokens Must Control The System — centralize all design values
75. Final Design Integrity Test — function, structure, visual, typography, color, interaction, states, responsive, accessibility, performance, recovery, consistency, novelty

## MASTER DESIGN LOOP
OBSERVE -> UNDERSTAND -> DECOMPOSE -> MODEL -> QUESTION -> IMPROVE -> DESIGN -> IMPLEMENT -> TEST -> COMPARE -> IDENTIFY PROBLEMS -> ROOT-CAUSE ANALYSIS -> CORRECT SYSTEMIC ISSUES -> RETEST -> POLISH -> VALIDATE

## FINAL DESIGN PRINCIPLE
Always ask: "Is this the best way to make the user accomplish the goal with the technology currently available?"
Not: "How can I make this look like something that already exists?"

THE DESIGN PROCESS DOES NOT END WHEN THE INTERFACE LOOKS FINISHED.
It ends when the system is: FUNCTIONAL + UNDERSTANDABLE + CONSISTENT + RESPONSIVE + ACCESSIBLE + RECOVERABLE + EFFICIENT + VISUALLY COHERENT + PURPOSEFUL + TESTED.
